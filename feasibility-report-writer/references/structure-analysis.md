# 可研样本文档结构分析

样本文档: `【可研】市发改委综合管理大系统（2026年升级改造）项目.docx`

## 1. 文档整体特征

- 段落数约 `2592`
- 表格数 `35`
- 内嵌图片约 `27`
- 一级章节 `9` 个
- 实际使用标题层级最深到 `Heading 7`
- 文档同时覆盖背景、现状、必要性、设计、建设内容、预算、建设管理、附项资料，属于较完整的政务信息化标准可研

## 4. 层级展开规律

- 一级标题用于章节切换，风格正式、概括性强。
- 二级标题用于标准条款位，如背景、目标、现状、预算、招标方案。
- 三级到五级标题常用于“系统 - 子系统 - 模块 - 子模块”逐层拆解。
- 六级和七级标题只出现在建设内容最复杂处，用于功能点或展示项清单。
- 这说明可研写作不是所有章节都要写到很深，只有“建设内容”和部分“需求分析”章节需要深拆。

## 5. 内容组织方式

### 叙述型段落

- 主体正文多为长段说明，适合背景、必要性、风险、治理制度、效益分析。
- 正文语气客观、审慎，少口号和宣传表述。

### 枚举型段落

- 常见 `（一）`、`（二）` 等中文序号
- 常见 `(1)`、`(2)` 等阿拉伯序号
- 常见 `数据类型：`、`数据来源：` 这种冒号引导式短引语

### 表格型内容

样本文档中表格密度高，主要用于：

- 成效考核指标表
- 现有系统清单
- 机房或设备分布表
- 数据资源现状表
- 密码保障现状表
- 建设必要性政策依据表
- 服务对象与用户量表
- 角色权限表
- 投资估算与预算汇总表

结论:
- 可研不是纯大段文字文档，表格是核心表达手段之一。
- 任何带“清单、指标、用户量、投资、职责、计划”的内容，都优先考虑用表格写。

## 6. 文风与规范

- 用词偏正式公文风，避免营销、承诺式、投标响应式表达。
- 项目效益写法多用“有助于、支撑、提升、促进、预计”。
- 风险章节不是空泛提醒，而是“风险 + 控制措施”配对。
- 预算章节先写编制说明，再给分类估算和汇总。
- 建设管理章节覆盖组织、招标、周期、质量、资金、制度，不只写进度。

## 7. 样式与版式线索

从样式抽取可见：

- `Heading 1`: 华文中宋、18pt、加粗、约双倍行距
- `Heading 2`: 黑体、16pt、加粗
- `Heading 3`: 楷体、15pt、加粗
- `Normal`: 仿宋、14pt、首行缩进约 2 字

这说明样本文档遵循常见政务正式材料版式：

- 标题层级通过字体家族切换强化识别
- 正文以仿宋类字体承载正式叙述
- 一级到三级标题风格鲜明，便于生成后再做 Word 样式映射

## 8. 写作时应复用的骨架规则

- 固定保留“单位概况 - 项目概述 - 现状 - 必要性/需求 - 设计 - 建设内容 - 预算 - 建设管理 - 其他”主线。
- 对信息化项目，必须显式写出现状、需求、架构、预算、实施管理，不可只写功能方案。
- 建设内容章节要按系统、子系统、模块逐层展开。
- 预算必须与建设内容相呼应，不能脱节。
- 招标方案和运行管理在政府项目可研里常常是必填项。

## 9. 技能设计启发

基于该样本，写作技能应具备这些能力：

- 根据输入材料先搭完整目录，再逐章扩写
- 自动识别哪些章节适合表格表达
- 对软件开发、系统集成、运维续建等不同项目类型做轻度结构调整
- 控制措辞，避免写成招标书、宣传稿或技术白皮书
- 在缺材料时输出“保守草稿 + 待补事实”，而不是编造数字

## 10. 每章叙事特点

以下规律来自样本文档的实际展开方式，不是抽象目录说明。

### 第一章 单位概况

- 这一章很短，但不是空白介绍。
- 重点是交代职责边界、业务属性、项目牵头关系，为后文“为什么要建”提供组织背景。
- 写法偏行政说明，段落简洁，不做技术展开。
- 常见结构是“单位职责 + 所承担的业务工作 + 与本项目的关系”。

### 第二章 项目概述

- 这一章承担全篇总览功能，信息密度高。
- 不是简单罗列项目名、周期、目标，而是按“项目对象 -> 建设背景 -> 建设目标 -> 建设内容 -> 周期 -> 效益 -> 风险 -> 指标 -> 投资概况”完整铺开。
- 样本文档在这一章就已经按子系统、模块、场景开始分层叙述，说明“项目概述”并不只是摘要，而是对后文全篇的先行压缩展开。
- 效益部分不是一句话总结，而是按经济、社会、管理等维度分别展开，且每个维度又能下钻到子系统或场景。

### 第三章 数字化现状

- 这一章整体较克制，强调“现状盘点”而非方案宣讲。
- 叙事重点是已有系统、网络资源、数据资源、安全基础和大模型建设现状。
- 常见写法是“先总后分”：先写整体框架，再列现有系统和资源，再引出数据与安全短板。
- 表格承担较大作用，尤其用于系统现状、数据资源、密码应用、安全现状。
- 这一章不追求长篇抒情，而追求“后文需求分析有依据”。

### 第四章 项目建设必要性及需求分析

- 这是样本文档论证最强的一章之一。
- 结构上通常是“必要性 -> 目标需求 -> 业务功能/流程/业务量 -> 用户角色 -> 资源测算 -> 性能要求 -> 安全要求 -> 数据要求”。
- 叙事方式明显偏“需求说明书化”，不是泛泛谈必要性。
- 模块展开非常深，尤其 4.2、4.3、4.5，会逐层写到子系统、模块、子模块、指标或流程步骤。
- 这章的核心不是“为什么值得做”一句话，而是把“需要做什么、做到什么程度、面向谁、处理多少量、性能和安全要到什么级别”讲透。
- 如果用户想要“可研骨架 + 系统需求说明书”风格，这一章是最重要的模板来源。

### 第五章 项目设计方案

- 这一章不是通用技术架构模板，而是对第四章需求的回应。
- 结构通常为“建设目标与规模 -> 总体架构及技术路线 -> 标准规范设计”。
- 样本文档会按子系统分别写总体架构图和技术路线，说明设计章节必须与具体建设对象绑定，不能只给统一的技术栈说明。
- 这一章应该回答“为什么这样设计才能支撑前面的需求”，而不是单独炫技术。

### 第六章 项目建设内容

- 这是样本文档篇幅最大的章节，也是最接近详细建设说明书的章节。
- 真正的写法不是“模块清单 + 一句功能概述”，而是逐层下钻：
  - 子系统
  - 一级功能模块
  - 二级功能模块
  - 具体功能点/页面/场景
- 也就是说，系统层不是终点。只要存在模块线索，正文就应继续落到模块和功能点层。
- 在深层级功能点下，正文通常会直接解释该功能处理什么信息、支撑什么业务动作、如何呈现分析结果、形成什么管理能力。
- 表格会用于功能明细汇总，但核心内容仍然靠正文展开。
- 这章是“15万字拉开差距”的关键来源。当前短稿之所以只有 1 万多字，主要就是没有把这一章按样本方式展开。
- 样本文档的“长”并不是废话堆积，而是每个重点模块都会继续回答这些问题：
  - 面向什么业务对象或管理对象
  - 当前有哪些信息、流程或监管痛点
  - 需要建设什么功能、看板、分析能力、流程环节或控制机制
  - 这些功能处理哪些数据、展示哪些信息、触发哪些业务动作
  - 最终形成什么样的监管能力、分析能力、服务能力或管理效果
- 也就是说，长度来自“需求维度展开”，而不是“同义改写”。

### 第七章 项目预算

- 预算章节不是只给一个总价。
- 样本文档会先写预算编制说明，再做分类估算、汇总、密码应用预算、年度使用计划。
- 很多预算表和测算表直接和具体建设模块、数据治理事项、工作量单位挂钩。
- 说明预算章节要和前面建设内容一一对应，而不是孤立财务页。

### 第八章 项目建设与运行管理

- 这一章偏实施与治理，不只是写“项目计划”。
- 典型内容包括组织机构、招标方案、建设周期、进度质量资金管理、制度安排。
- 叙事重心是“怎么保障项目能被正确建设和长期运行”，因此常与责任分工、制度、验收、运维要求相联系。

### 第九章 其他

- 这一章是附件型章节，但在正式可研里很有作用。
- 常放预算依据、技术经济资料、物理布置图、研究成果等。
- 它起的是“为前文论证补证据”的作用，不应简单删除。

## 11. 章节长度与展开深度规律

- 样本文档虽然只有 9 个一级章节，但正文总量很大，原因不是每章平均拉长，而是第 4 章和第 6 章极度细化。
- 第一章和第三章偏短，主要承担背景与现状盘点。
- 第二章中等偏长，承担总览和预埋。
- 第四章很长，因为它把需求、流程、角色、数据量、性能、安全、数据要求全部拆开。
- 第五章中等偏长，负责把需求映射到设计。
- 第六章最长，负责把设计落到系统、模块、功能点、场景、数据能力。
- 第七、八章也不短，因为预算和建设管理在正式可研中必须成体系。

## 12. 从参考样本提炼的长文写作原则

- 长文不是一次性写完，而是“先骨架、后章节、再子系统、再模块、最后通篇校核”。
- 每章应有自己的叙事使命，不能所有章节都用同一种写法。
- 长文拉开篇幅的关键不是堆套话，而是：
  - 对每个子系统展开
  - 对每个模块展开
  - 对每个流程、角色、数据对象、指标、工作量展开
  - 对每个风险、预算、管理机制展开
- 长文质量的关键也不是“写得多”，而是“每个展开单元都增加了信息维度”。常见有效扩展维度包括：
  - 业务对象
  - 触发场景
  - 流程动作
  - 数据来源与数据流向
  - 指标与展示结果
  - 管理控制点
  - 预期成效
- 第四章和第六章应分多轮输出，单轮只处理一个子系统或一个主题簇，避免一次性生成粗糙长文。
